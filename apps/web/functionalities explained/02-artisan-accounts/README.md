# Artisan accounts (entry, sign-up, login, logout, session)

An artisan who opens the app chooses "I am new" or "I have an account". A new artisan fills in name, phone, username, password (twice), trade and a short description, and is registered and logged in at once. An existing artisan logs in with username and password; the nine seeded demo artisans use their lower-case first name and one shared demo password. Logging out returns to Home.

## How it works

### Sign-up

1. Home -> "I am an artisan" (`home.artisan`) -> `actions.go('artisanEntry')` because `ui.actingArtisanId` is `null`.
2. `ArtisanEntry` shows two big buttons: "I am new" (`entry.new`, `actions.go('artisanSignup')`) and "I have an account" (`entry.existing`, `actions.go('artisanLogin')`). Both screens have `back="home"`.
3. `ArtisanSignup` keeps seven local `useState` fields (`name`, `phone`, `trade`, `username`, `password`, `confirm`, `description`) and an `error: Key | null`. On submit (`<form noValidate>`, so the browser does not validate; the store does) it calls:

```ts
const r = actions.registerArtisan({ name, phone, trade, description, username, password, confirm });
if (!r.ok) setError(r.error);
```

4. `registerArtisan` (store/index.tsx) validates in this exact order and returns `{ ok: false, error: <Key> }` at the first failure:
   1. `name.trim().length < 2` -> `signup.errName`
   2. `resolveTrade(trade)` returns `null` -> `signup.errTrade`
   3. `checkNewCredentials(username, password, confirm, artisans)` fails -> mapped to `signup.errUsername` (`username_format`), `signup.errUsernameTaken` (`username_taken`), `signup.errPassword` (`password_short`), `signup.errConfirm` (`password_mismatch`)
   4. `normalizePhone(phone)` returns `null` -> `signup.errPhone`
   5. another artisan already has that normalised phone -> `signup.errTaken`
5. If all pass it builds the `Artisan`:
   - `id: uid('artisan')`, `name: cleanName`, `phone: normalized`, `trade: tradeKey`, `neighbourhood: NEIGHBOURHOOD`, `description: description.trim()`;
   - defaults `baseRating: 0, baseJobs: 0, avgResponseMin: 20, priceMin: 3000, priceMax: 8000, seedVerified: false, isSeed: false`;
   - credentials from `makeCredentials(username, password, uid('salt'))`: `{ username (normalised), salt, passwordHash }`. The password itself is never put in the object.
6. It calls `rememberPassword(normalized, password)` (client.ts, in-memory maps only), then `dispatch({ type: 'register', artisan, at: now(), ids: ids(4) })`.
7. The reducer `register` case appends the artisan, creates SMS and an audit entry, and logs the new artisan in (see "File by file / reducer").
8. In API mode `mirror()` runs `bridge.registerArtisan(artisan)` in the background and then stores the returned backend id with `dispatch({ type: 'patchArtisan', id, patch: { remoteId } })`.
9. `registerArtisan` returns `{ ok: true, id }`. The screen is already `artisanStatus` (set by the reducer), so the sign-up component unmounts.

### Login

1. `ArtisanLogin` has `username` / `password` fields and an `error`. Submit calls `actions.loginArtisan(username, password, next ?? state.ui.loginNext ?? undefined)`.
2. `loginArtisan` calls `verifyLogin(artisans, username, password)`. On `null` it returns `{ ok: false, error: 'login.errWrong' }`: one message for unknown user, wrong password and rejected account. The screen then calls `setError(r.error); setPassword('')` (password field cleared, username kept).
3. On success it calls `rememberPassword(artisan.phone, password)` and dispatches `{ type: 'login', artisanId, next: next ?? ui.loginNext ?? 'artisanStatus' }`.
4. Reducer `login`: `ui: { ...ui, actingArtisanId, screen: a.next, loginNext: null }`.
5. Where `next` comes from: when another artisan screen (`ArtisanStatus`, `ArtisanInbox`, `ArtisanComplete`) is opened with nobody logged in, it returns `<ArtisanLogin next="..." />` inline (for example `next="artisanInbox"`), so after login the user lands on the screen they wanted. `Tracking.tsx` also calls `actions.go('artisanLogin', { actingArtisanId: null, loginNext: 'artisanInbox' })`, which is the only place that sets `ui.loginNext`.
6. The login screen also has "Create account" (`login.create`, goes to `artisanSignup`) and a notice `login.demo` that prints the demo usernames and the demo password (`{password}` = `DEMO_PASSWORD`).

### Logout

`ArtisanStatus` shows `login.loggedAs` ("Logged in as {name}") and a link button `login.logout` calling `actions.logout` -> `dispatch({ type: 'logout' })`. Reducer: `ui: { ...ui, actingArtisanId: null, loginNext: null, screen: 'home' }`. Nothing else is cleared (artisans, vouches, jobs stay).

### Session

There is no token. The "session" is `state.ui.actingArtisanId`, part of the persisted state (`localStorage['acbridge.demo.v2']`). A page refresh keeps the user logged in (test: "survives a refresh"). Closing the browser does not log out.

## File by file

### `apps/web/src/screens/ArtisanEntry.tsx`
Stateless. Uses `Screen` (`entry.title`, `entry.instruction`) with hints `entry.newHint` and `entry.existingHint`. Icons: new account, key.

### `apps/web/src/screens/ArtisanSignup.tsx`
- Fields: name (`autoComplete="given-name"`), phone (`inputMode="numeric"`, placeholder `signup.phoneHint` "Example: 670123456"), username (`autoCapitalize="none"`), password and confirm (`type="password"`, `autoComplete="new-password"`), `TradeField` (`signup.trade`), a read-only neighbourhood input showing `common.neighbourhood`, and a description textarea.
- Editing username, password, confirm or trade clears the error (`setError(null)`); editing name, phone, description does not.
- Voice dictation: `getRecognition()` returns `window.SpeechRecognition ?? window.webkitSpeechRecognition ?? null`. If available, a microphone button (`signup.mic` / `signup.micOn`) toggles a recogniser with `lang = speechLocale[state.lang]` and appends the first transcript to the description. If unavailable the button is not rendered. Errors while starting are swallowed.
- The error box is `<div role="alert" className="error" hidden={!error}>`; it stays in the DOM, hidden when empty, so tests can query `getByRole('alert')` after an error.
- Submit button: `signup.submit` ("Register"/"S'inscrire").

### `apps/web/src/screens/ArtisanLogin.tsx`
Props: optional `next?: Screen`. Renders `Screen` with `back="home"`. Use of `state.ui.loginNext` as fallback as described. Shows `login.errWrong` in the alert box.

### `apps/web/src/domain/security.ts` (credentials part)
- `PASSWORD_MIN = 8` (same minimum as the backend `RegisterIn.password`, per the comment).
- `hashSecret(secret, salt)`: builds a 16-hex-character string from two FNV-1a "lanes" (seeds `0x811c9dc5` and `0xdeadbeef`) over `salt\0secret\0salt`, followed by 2000 extra mixing rounds per lane. The file states it is demo-grade only and not cryptographically secure; the real backend uses Argon2id.
- `normalizeUsername(u)`: `u.trim().toLowerCase()`.
- `isValidUsername(u)`: normalised value must match `/^[a-z0-9._-]{3,20}$/`. Because of the normalisation, `Grace` and `GRACE` are the same user. The character class is `a-z 0-9 . _ -`, so underscore is accepted (the `signup.usernameHint` placeholder says "Letters, numbers, dot, dash (3 to 20)" and omits it, while `signup.errUsername` lists it).
- `checkNewCredentials(username, password, confirm, artisans)` returns `{ ok: true }` or `{ ok: false, reason }` with the check order: format, uniqueness (`artisans.some((a) => a.username === n)`), password length, confirmation.
- `makeCredentials(username, password, salt)` returns `{ username: normalised, salt, passwordHash }`.
- `verifyLogin(artisans, username, password)`: finds by normalised username; always computes `hashSecret(password, a?.salt ?? 'no-such-user')` even for unknown users (same work for both failures); returns the artisan only if it exists, is not `rejected`, and the hashes are equal; otherwise `null`.

### `apps/web/src/store/index.tsx` (account actions)
Documented in "How it works". Extra detail: `registerArtisan` and `loginArtisan` are synchronous and return their result; only the backend mirroring is asynchronous. `uid(prefix)` builds ids from `Math.random()` and `Date.now()`; `ids(n)` returns n unique event ids used for the SMS and audit rows.

### `apps/web/src/store/reducer.ts` (account cases)
- `register`: appends `a.artisan` to `artisans`; creates `sms.vouchRequest` to the phones of `seed-1` and `seed-2` (params `name`, `phone`, `trade`) with ids `a.ids[0]`, `a.ids[1]`; `sms.welcome` to the new artisan (`a.ids[2]`); an audit entry `kind: 'verification'`, `{ event: 'registered', name }` (`a.ids[3]`, rendered as `audit.registered`); and sets `ui: { ...ui, actingArtisanId: art.id, screen: 'artisanStatus' }`.
- `login` and `logout`: as described above.

### `apps/web/src/data/seed.ts`
`RAW` holds nine seeded artisans (`seed-1` Grace plumbing, `seed-2` Paul electrical, `seed-3` Esther, `seed-4` Peter, `seed-5` Samuel (pending, not verified), `seed-6` Rose tailoring, `seed-7` Daniel carpentry, `seed-8` Fabrice mechanics, `seed-9` Blaise plumbing). `SEED_ARTISANS` maps each to an `Artisan` with `username = name.toLowerCase()` and `makeCredentials(username, DEMO_PASSWORD, 'seed-' + username)`. Passwords are computed at module load, not stored as plain text but the shared demo password is public (`login.demo` prints it). Seeded accounts therefore log in with e.g. `grace` / `Demo-Pass-123!`.

### `packages/core/src/phone/index.ts` (`normalizePhone`)
`normalizePhone(raw, prefix = '+237')`: strips spaces, `-`, `(`, `)`, `.`; a 9-digit number starting with 6 gets `+237`; `237` followed by 9 digits gets a leading `+`; the result must match `/^\+[1-9]\d{7,14}$/` or `null` is returned. It mirrors `normalize_phone` in `backend/app/schemas.py` (per its comment). `maskPhone` and `stripPhones` in the same file are not used by this flow.

## Data and state

`Artisan` (types.ts) fields written at sign-up: `id`, `name`, `phone` (E.164), `username` (lower case), `salt`, `passwordHash`, `trade`, `neighbourhood`, `description`, `baseRating 0`, `baseJobs 0`, `avgResponseMin 20`, `priceMin 3000`, `priceMax 8000`, `seedVerified false`, `isSeed false`; later `remoteId` (API mode), `operatorApproved`, `rejected`.

State touched: `artisans`, `sms`, `audit`, `ui.actingArtisanId`, `ui.screen`, `ui.loginNext`. All of it is persisted in `localStorage['acbridge.demo.v2']`, including `salt` and `passwordHash`. The plain password is kept only in the in-memory `passwords` map of `api/client.ts` (not persisted; lost on refresh).

## Rules and edge cases

| Rule | Where | Message key |
|---|---|---|
| Name at least 2 characters | store `registerArtisan` | `signup.errName` |
| Trade at least 2 characters after normalisation | store -> `resolveTrade` | `signup.errTrade` |
| Username 3-20 chars of `a-z 0-9 . _ -` (case-insensitive) | `security.isValidUsername` | `signup.errUsername` |
| Username unique | `security.checkNewCredentials` | `signup.errUsernameTaken` |
| Password at least 8 characters | `security.checkNewCredentials` | `signup.errPassword` |
| Password equals confirmation | `security.checkNewCredentials` | `signup.errConfirm` |
| Valid phone (Cameroon mobile or E.164) | `normalizePhone` | `signup.errPhone` |
| Phone not already registered | store | `signup.errTaken` |
| Wrong user / password / rejected account | `verifyLogin` | `login.errWrong` (same text for all) |

- The reducer's `register` does not re-validate; the store function is the guard. Tests call the reducer directly with ready-made artisans.
- A rejected artisan (operator pressed Reject) cannot log in, but an already-open session of that artisan is not closed.
- Username uniqueness is checked against `a.username === normalised`, so seeded names (`grace`) are reserved.
- Phone numbers are unique per artisan only; a customer or another role is not checked.
- Registration immediately logs the artisan in and sends two vouch-request SMS to Grace and Paul regardless of the artisan's trade.

## Backend connection

Only in API mode (`apps/web/src/api/bridge.ts` `registerArtisan`): `POST /auth/register` (role `ARTISAN`, errors ignored so an existing user is fine), `POST /auth/login` (through `login(phone)` in `client.ts`, using the typed password remembered by `rememberPassword`, or `DEMO_PASSWORD` for seeded users), `POST /artisans` (profile: full name, location `"<NEIGHBOURHOOD>, Buea"`, description), then `POST /artisans/{id}/skills` with the backend skill for the trade (only possible for the 7 catalogue trades; a free-text trade throws and the account stays local, shown as a notice). The local login itself never calls the backend: it checks the locally stored hash. The username is not sent to the backend (the backend identifies users by phone).

## Known limits and what changes in the production rebuild

- Password hashing is a stretched FNV-1a made for demos. Production needs a real password hash (the backend uses Argon2id) and the check must happen on the server.
- Credentials, hashes and salts sit in `localStorage`, readable by anyone with the browser; there are no tokens, expiry, rate limiting or lockout, and no password reset.
- The seeded artisans share a public password.
- Registration does not verify phone ownership (no OTP); SMS are simulated.
- Local username and backend identity are separate: in API mode the backend knows only phone and password.
- Login "next" routing relies on `ui.loginNext` and a `next` prop; there are no real sessions to resume.
